# Spike: Query & Check Mechanism (Chat Prototype)

Prototypes part 3 of the [top-level readme](../../readme.md)'s three-layer
architecture — the **Query & Check Layer** — on top of the graph proven out
in [`graph-ingestion3`](../graph-ingestion3/): natural-language questions
and situational checks against the Policy System knowledge graph, answered
with full provenance back to source regulation text.

## Status

Question catalog (39 questions, two passes), test data, golden
answers/rubrics, and both candidate query mechanisms are in place.

6. [`q-approach2.md`](./q-approach2.md) / [`query_mechanism_v2.py`](./query_mechanism_v2.py) / [`test_query_mechanism_v2.py`](./test_query_mechanism_v2.py) — agentic tool-use over the live graph for the 13 questions approach 1 can't reach (M3, M5, M14, H1, H3, H5, H6, H8, H9, H11, H12, H13, H14), falling back to approach 1's template router first. Built after a framework survey initially recommended FalkorDB's own `GraphRAG-SDK`; installing and inspecting it directly (not just reading its docs) found its actual API is a document-ingestion + hybrid-chunk-retrieval package with no Local/Global Search or community-summarization support at all despite what its web documentation describes. 22/22 plumbing tests pass against a scripted fake client. **Run for real** against a local Ollama server across three models: `qwen3:14b`, `qwen2.5-coder:14b`, and `qwen3-coder-next:q4_K_M` (51GB, user-recommended for tool calling). The mechanism's plumbing never failed once; the models found a growing list of distinct Cypher-writing failure modes — wrong properties, wrong ID-pattern matching, reversed relationship direction, a tool-calling protocol miss. **The key finding**: the graph schema had only ever been given to the model inside one tool's argument description, never in the system prompt — moving it into the system prompt (plus fixing a misleading example sitting next to the exact case it misled on) eliminated the ID-pattern and relationship-direction failures in both retested cases, tested directly rather than assumed. What's left after that fix is shallower — stopping exploration early, under-citing retrieved rows — not wrong-Cypher-shape mistakes. One more bonus along the way: `qwen3-coder-next`'s own query exploration caught a real gap in `golden-answers.md`'s own H1 entry (two GDPR Art. 32 sub-clauses missing from the original golden reasoning, now corrected there). Full results in `q-approach2.md`'s "Result" and "Grounding location matters" sections.

7. [`experiment_self_consistency.py`](./experiment_self_consistency.py) / [`experiment_temperature.py`](./experiment_temperature.py) / [`experiment_validator_loop.py`](./experiment_validator_loop.py) / [`experiment_union_plus_validator.py`](./experiment_union_plus_validator.py) — four standalone experiments (not wired into the mechanism) testing fixes for the "stops early / under-cites" failure left over after the grounding fix. **Self-consistency** (sample the agent 3x, combine): union across runs reached 7/7 on the test question, but strict-consensus/majority-vote reached 0/7 — the runs didn't cluster near a right answer the way classic self-consistency assumes, they spanned "fully correct" to "no answer at all," so union (not voting) is the strategy with real evidence behind it. **Temperature** (does lowering it reduce that variance?): tested at default, 0.1, and 0.0 — lower temperature made outcomes *worse*, not better, consistently across two settings. **Generator + validator critique loop**: the validator correctly caught a real gap once, but the auto-revise loop shared its turn budget with the original exploration and didn't converge. **Combining union + validator** (pool evidence from 3 runs, one synthesis call, one validation call, no open-ended loop): performed *worse* than plain union — the synthesis step only extracted 4/7 despite having all the right evidence pooled in its context, and the validator, which had correctly caught a real gap in the standalone test, passed this incomplete answer without complaint. Net finding across all four: **mechanical combination (regex-extract cited ids, take the union) beats every tested form of LLM-driven combination** — more LLM judgment steps didn't reliably realize the benefit of more evidence, they lost it. Full tables and discussion in `q-approach2.md`'s "Further experiments" section.

8. [`experiment_validator_grounding.py`](./experiment_validator_grounding.py) — tested whether the validator's false PASS above had the same root cause the generator's earlier failures did (no graph schema in its prompt, just a checklist). `GRAPH_SCHEMA` was factored out of `query_mechanism_v2.py`'s `SYSTEM_PROMPT` into its own constant (pure refactor, byte-identical, both suites still pass) and reused in a new `VALIDATOR_SYSTEM_GROUNDED`. Controlled comparison — the *same* pooled trace and *same* 5/7 draft answer, validated twice, only the prompt differing: both the schema-grounded and ungrounded validator **PASSed the same incomplete answer**. The fix that resolved the generator's Cypher-writing mistakes didn't transfer to the validator's completeness judgment — different failure shape (a knowledge gap vs. a long-context attention/auditing gap) that happened to look similar because both looked like "give the model more context."

9. [`q-approach3.md`](./q-approach3.md) — **reflections only, no accompanying code**. Before spending more of this spike re-deriving fixes by trial and error, checked whether the two residual failure classes above (relationship-direction reversal; stopping early/under-citing) are already solved elsewhere. Answer is split: relationship-direction correctness in generated Cypher **is** solved, deterministically, by existing tooling (a public "Cypher Direction Competition" and its winning solution, shipped as LangChain's `CypherQueryCorrector` — parse-and-correct against the schema, no model judgment involved, categorically different from every prompt-based mitigation tried in this spike). The broader "agent completely and correctly traverses a multi-hop graph" problem is **not** solved — it's active research (Think-on-Graph, Plan-on-Graph, 2026 GraphRAG recall work), with Plan-on-Graph's "adaptive exploration breadth + self-correct erroneous paths" mapping closely onto our stopping-early/under-citing failure specifically, but untested against a graph this small (ToG/PoG were benchmarked on large sparse KGs like Freebase/WikiData, not an 8-label/8-edge-type graph like ours). The validator research (self-correction blind spot, cross-model verification, lost-in-the-middle) explains *why* our validator experiments behaved as they did, without handing us a working validator. Two concrete, different-in-kind next steps identified: adopt deterministic direction-correction (low-risk, high-confidence transfer), and separately test whether an adaptive-breadth restructuring is solving a problem this graph's scale actually has before committing to building it.

The corrector fired in 2 of 7 — on `EXPRESSES`, `SATISFIED_BY`, and `IMPLEMENTED_BY`, none of them the two originally-documented hops, real evidence it generalizes rather than being overfit to H1/H11 specifically — and one of those firings turned H1/`qwen3-coder-next`'s prior wrong "non-compliant" into a materially better (though still rubric-incomplete) "partial." ## Why start with questions, not architecture

"Build a chat interface over the graph" under-specifies the hard part. A
question like *"What roles does GDPR define?"* is one Cypher query. A
question like *"Is this new API endpoint compliant with GDPR Article 32?"*
requires mapping free-text about a system into a Capability, then reasoning
about whether a Control exists and passed — and today's graph has no
Control data wired to real regulations to reason over at all. Those two
questions can't share one naive "translate NL to Cypher and run it"
strategy. Cataloging question difficulty first is what tells us where a
single NL→Cypher translator is enough, and where we need retrieval +
multi-hop reasoning + an honest "I don't have that data yet."

## Data reality check (as of this spike's start)

The chat prototype can only be as honest as the graph it sits on. Current
state, loading `cra.json` + `nis2.json` + `gdpr.json` per
[`graph-ingestion3`](../graph-ingestion3/README.md):

| Layer | Status |
|---|---|
| Regulation → Role → Requirement → Obligation → Capability | Populated for real regulations: 3 Regulations, 13 Roles, 277 Requirements, 339 Obligations, 90 Capabilities |
| Cross-regulation Capability convergence | Workflow exists (`find_capability_duplicates.py` / `merge_capabilities.py`), but `capability_merges.json` is currently **empty** — no merges have actually been applied, so the 90 Capabilities above are not yet deduplicated across regulations |
| Capability → Policy → Standard → Control | Only exists in `policy_system_graph.json`, the **hand-built worked example** (2 Policies, 2 Standards, 2 Controls). Not connected to any real CRA/NIS2/GDPR data |

This means: today, questions that stop at Obligation/Capability are
answerable against real data. Anything that needs a Policy, Standard, or
Control — or a *merged* cross-regulation Capability — is either answerable
only against toy data or not answerable at all. See the status tags in
`example-questions.md`.

**Superseded by the Helvex spike below** — the Policy→Standard→Control row
above is no longer accurate. Helvex's synthetic layer governs 13 real
CRA/NIS2/GDPR capabilities (not just its own new one), so real
Requirement→...→Control chains now exist for GDPR and CRA. See
[`golden-answers.md`](./golden-answers.md) for the current, verified state
of every question in the catalog.
